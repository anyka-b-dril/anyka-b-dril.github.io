I restructured the appointment manager’s architecture to decouple the data storage from the business logic, refined data actions to mirror standard data lifecycle methods, and added an executable terminal view as a user interface. Although the architecture refactoring has made the application more scalable and maintainable, the appointment manager still lacked data persistence and concurrency.</p>

    <p>In this advancement cycle, I replaced the in-memory data repository, which utilized a hash map, with a MongoDB repository. First, I added the official MongoDB Java driver to the project object model file, enabling the application to connect securely and fully use MongoDB's capabilities. By including the driver, I show that I can manage external dependencies with standard industry tools. Next, to bridge the application and data layers, I implemented a database configuration file that centralizes the connection logic for the MongoDB service. The Mongo repository calls upon the database configuration to initialize the MongoDB connection. To prevent application errors or timeout delays, the class immediately validates that the database server is reachable and responsive with a ping test. The repo contains all necessary CRUD operations using standard MongoDB methods, such as insertOne and deleteMany. Additionally, the findAll method uses an index, which enforces the appointments to be listed out chronologically. By implementing a MongoDB index, I demonstrate my proficiency in database administration and my ability to design applications with data growth in mind. Lastly, I developed an appointment mapper, a custom helper class that bidirectionally translates Java values to BSON, to ensure seamless data integrity. While the MongoDB Java Driver provides built-in mapping, a custom mapper allows for more scalability and complex constructors. Developing this helper class has deepened my practical knowledge of data serialization and highlights my understanding of object-document mapping.</p>
    <p>To confirm the appointment manager’s database stability, I added a MongoDB integration test to the JUnit suite. The integration test uses an isolated test database, appointment_test, to verify the success and failure behavior of all data operations. Although the integration test is necessary to guarantee both systems work harmoniously, integration tests execute much slower due to their dependence on multiple components and external services. In order to keep unit tests fast, I separated the integration test process using Maven's built-in *IT.java naming conventions and the Failsafe build plugin; unit tests run as Maven tests, and integration tests run as Maven verify. My commitment to separation of concerns and security showcases my skills in system integration, test automation, and environment management.</p>
    <p>Overall, by transitioning from in-memory data storage to an external database, I proved that I can modernize code, maintain system stability, and verify integrity through automated unit tests; thus, my project fully aligns with the outcome of designing and evaluating computing solutions that solve a problem using standard practices, while managing the trade-offs involved in design choices. As a widely used tool in the tech industry, choosing MongoDB reflects my knowledge of modern, enterprise-level tools and practices, aligning with the outcome of using well-founded and innovative techniques, skills, and tools in computing practices. Lastly, my commitment to standard practices and integration testing demonstrates my security mindset in application development and my acknowledgment of potential vulnerabilities and design flaws.</p>
    <p>The database project enhancement marks the first time I have set up a database with a Java application. At first, I was unsure how to make the database connection. Still, after researching the Java Mongo Driver, I learned that the database config file isolates the connection logic to MongoDB. However, once I implemented the driver, configuration logic, and the MongoAppointmentRepo class, my terminal became plagued with missing SLF4J binding warnings. Although it is not a requirement, the MongoDB Java Driver relies on SLF4J (Simple Logging Facade for Java) by default and automatically searches for the dependency upon initialization. To suppress the warnings and keep the terminal view clean, I added the classic Logback module to the project object model and created a logback.xml file. Suppressing the log output was somewhat confusing because I had never used Logback before. On top of that, this was the first time I had ever created an integration test. I was surprised to realize that the test would follow a similar outline to the appointment service test file, just with different syntax.</p>
    <p>Additionally, my original draft of the enhancement did not include managing the client lifecycle or making connection settings explicit. The MongoDB client creates an internal connection pool; reusing it conserves memory and lets the database service manage connections concurrently. Because I did not close the client connection in my initial draft, I found that the appointment manager was susceptible to memory leaks and interrupted data operations. Likewise, by not specifying the connection settings, I allowed the application to hang indefinitely if the connection was dropped or the database stalled. To address this, I specified the connection settings in the database config file and added a close method in MongoAppointmentRepo.java.</p>
